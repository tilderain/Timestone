  ...     ...     ...

--- 5b. cChrNode layout ---
  Offset  Size  Field
  ──────────────────────
  +0x00   8     vtable
  +0x08   8     mpChr (uCharacter*)
  +0x10   8     mpNext (next cChrNode*)
  +0x18   8     mpPrev (previous cChrNode*)
  ...     ...   ...

  Note: The first cChrNode is INLINE at cChrTeam + 0x08 (confirmed by the
  cChrTeam constructor calling cChrNode__cChrNode(param_1 + 1), which places
  the first node at the address + 8 bytes from the team base).

  Traversal:
    firstNode = team + 0x08                      // inline first node
    character = *(uint64_t*)(node + 0x08)         // uCharacter*
    nextNode  = *(uint64_t*)(node + 0x10)         // next cChrNode* (heap allocated)
    while (node) { read character; node = nextNode; }

--- 5c. uCharacter layout (per character, ~32KB each) ---
  Offset  Size  Field
  ──────────────────────
  +0x00   8     vtable
  +0x08   8     DTI pointer (contains size at DTI+0x34)
  +0x10   ...   Character state (action state machine, position, health, etc.)
  +0x14   ...   tagState
  ...     ...   ...
  +0x??   4     groundedState
  ...     ...   vector, specialState, anim, ...
  Size determined by DTI: *(uint32_t*)(character->dtiPtr + 0x34)

  DTI (Dynamic Type Information) is an Mt Framework concept. Each object
  has a DTI pointer at +0x08 (after vtable at +0x00). DTI + 0x34 holds the
  allocated size of this specific character's class (varies per character:
  Wolverine is smaller than Galactus).

 7. EXISTING CODE (rollback.cpp)
================================================================================

Location: UMVC3Hook/code/rollback.cpp
See the file for full source (~336 lines). Key architecture:

- Ring buffer: g_slots[ROLLBACK_WINDOW] of SnapshotSlot { data, size, capacity }
- Region list: BuildRegions() populates Region[] with { ptr, size } for all
  snapshot regions in a fixed order. Save and restore iterate identically.
- Physics: TODO — currently hooks FUN_140521df0 (actually sMain__move, not
  a physics function). The physics world (~11424 bytes) may be at
  sMain + 0x31A78 or a separate allocation. Full sMain dump covers it.

Snapshot regions (order is critical — must match between save and restore):
  1. sReplay          0x23400 bytes   (~144KB) — frame counter, replay buffer
  2. sShot            0x500 bytes     (1.25KB) — projectile base singleton
  3. sHitSolver       0x34080 bytes   (~208KB) — collision pairs + result buf
  4. aNextBattle      0x20000 bytes   (~128KB) — battle state machine
  5. sGameUI          0x6000 bytes    (~24KB)  — pause state, HUD data
  6. sMain            0x40080 bytes   (~256KB) — frame timing, pause flag
  7. sGameEffect      0x2000 bytes    (~8KB)   — gameplay effects
  8. sAction          0x300 bytes     (0.75KB) — game phase, round timer, hitstop
  9. Physics          11424 bytes     (~11KB)  — physics world (TODO: fix pointer)
  10. cChrTeam[0]     0x2C0 bytes     — team 0 health, meter, X-Factor
  11. cChrTeam[1]     0x2C0 bytes     — team 1
  12-17. uCharacter   DTI size (~32KB each) — 6 characters from linked-list traversal

Total per snapshot: ~700-900KB
Ring buffer (16 frames): ~14MB

KNOWN ISSUES:
  1. Physics hook hooks sMain__move instead of the real physics function.
     FUN_140521df0 is NOT a physics function — it's sMain__move (frame timing).
     The param_1 captured is likely sMain*, but the 11424-byte "physics world"
     is at some offset within sMain or a separate allocation.

  2. Per-character DTI size: uCharacter struct at +0x08 has a DTI pointer.
     *(uint32_t*)(dtiPtr + 0x34) gives the allocated size. This should be
     stable during a match (character classes don't change).

  3. sShot projectile list: Currently only saves the base singleton (0x500 bytes).
     The dynamically-allocated projectile nodes are NOT captured. Missing
     projectiles after restore will likely cause visual/functional desync.

  4. sGameEffect effects list: Same issue — base singleton saved but dynamic
     effect list is not.

  5. Input injection during re-simulation: After RestoreSnapshot, the caller
     needs to inject corrected inputs for each re-simulated frame. This is
     not yet implemented. The current F5/F6 test keys just blindly save and
     restore without re-simulation.

  6. The linked-list traversal assumes the first inline cChrNode is at
     cChrTeam + 0x08. This is confirmed by cChrTeam__getNextNode(team) calling
     cChrNode__getNext(team + 8). The first node's mpChr is at node + 0x08
     and mpNext at node + 0x10.

 9. CONTROLLER.CPP — INPUT DELAY ARCHITECTURE
================================================================================

The existing input handling (controller.cpp) uses a frame-delayed ring buffer:

  hkprocessFrameInput (hooked at 0x14002DD60):
    - Called per-character per-frame
    - Accumulates raw physical input into per-character storage
    - Looks up the delayed input from a ring buffer at index [currentFrame + delay]
    - The ring buffer stores full 32-bit input masks

  g_oldInputs[] and g_receivedInput[] (global state):
    - g_oldInputs[f % IN_BUF_SZ]: locally read input for frame f
    - g_receivedInput[f % IN_BUF_SZ]: remotely received input for frame f

  Frame counting:
    - g_netFrameCount = absolute frame counter, incremented each frame
    - sReplay + 0x54 = game's own frame counter (master clock)
    - g_delayFrames = configured delay (1-15, sent over wire)

  This is a DELAY-BASED system, not rollback. To convert to rollback:
    1. Replace the ring-buffer lookup with snapshot restore + re-simulation
    2. When late input arrives for frame N,:
       a. Rollback_RestoreSnapshot(N)
       b. For f = N to currentFrame:
            - inject corrected input from g_receivedInput
            - run the full sMvc3Main__move frame
            - Rollback_SaveSnapshot(f+1) with corrected state

 10. DEFAULTs.H — PROTOTYPE ROLLBACK CODE (for reference)
================================================================================

Location: UMVC3Hook/code/defaults.h

Contains a SaveLoadState() function that was a prototype for rollback:
  - Uses a flat SaveMemory vector (byte buffer) with SaveLoadPtr macros
  - Saves: fighting data (0x140d44a70), mysterydata (0x140d533e0), physics
  - Physics: hooks FUN_140521df0 (actually sMain__move), saves 11424 bytes
  - Per-character: reads from mysterytable + 0xaa0 + (0x438 * i) stride
  - Contains runahead code that attempts re-simulation but is commented out
    because "physics doesn't work during runahead"

The Fighter/ScriptableFighter structs in defaults.h are a partial mapping of
uCharacter with known fields at specific offsets. Much of the offset data is
unreliable/outdated.
