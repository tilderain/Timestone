Rollback Character Restore Audit, Revised
=========================================

This document revises resnap2.txt after re-reading the current snapshot and
restore code and re-checking the live Ghidra database at port 8192.

The important correction is this:

    A byte not named in CCHR_SCALAR_RESTORE_RANGES is not necessarily absent
    from restore. The character body is first copied broadly, then pointer-like
    qwords are overlaid with live values, then explicit scalar and subobject
    fixups run. The real question is whether a field is restored deterministically
    after the pointer overlay and after native post-restore repair.

Several statements in resnap2 called broad gaps "missing" even though the
initial body copy restores them when IsLikelyPointer() does not misclassify
them. Those statements are downgraded below to "not explicitly classified".

Source of truth
--------------

Current character restore path:

1. Snapshot captures each roster character at its DTI-sized body.
2. Restore copies body bytes from +0x08 onward.
3. It preserves every qword for which either saved or live value passes
   IsLikelyPointer(). IsLikelyPointer only checks:

       0x10000 <= value < 0x800000000000 and (value & 7) == 0

   It does not require accessibility, a valid DTI, ownership, or a pointer
   field classification.
4. CCHR_SCALAR_RESTORE_RANGES repairs selected inline scalar ranges.
5. ConcreteCharacterSnapshot_RestoreFields applies generated concrete-tail
   fields and its own pointer/scalar heuristic.
6. Motion buffers, target-info records, hit primitives, attack target tables,
   and cChrInput receive separate fixups.
7. Rollback_ClearStalePointers runs after body, scalar, subobject, and concrete-
   tail restoration.
8. Shot/effect reconstruction and model render-state repair run.
9. CCHR_POST_RESTORE_TAIL_RANGES and the mpThrowPairChr pointer at +0x6730 are
   reapplied after reconstruction.
10. Active-character UI and camera scalar synchronization run last.

The most destructive confirmed implementation defect makes this worse than an
explicit-policy problem alone: stale-pointer cleanup walks 64 qwords where
native code defines only 21. cChrInput also crosses its verified object boundary
by 0x30 bytes into mCmdSpatk; that boundary violation is confirmed, although its
runtime effect has not been isolated independently.

Verified cChr layout
--------------------

Ghidra's cChr structure is 0x68F0 bytes. Relevant offsets are:

    +0x0000  inherited uCharacter/uModel/uActorGameModel
    +0x14F0  mChrF through mDbgF and flag state
    +0x1560  cChrAbility, size 0x318, ends at +0x1878
    +0x1878  cAtkCtrl, embedded size 0x950, ends at +0x21C8
    +0x21C8  cChrInput, aligned extent 0x570, ends at +0x2738

The cChrCmd fields reported by Ghidra are at:

    +0x2738  mCmdSpatk, size 0x218
    +0x2950  mCmdCombo, size 0x218

Those offsets are authoritative for the current x64 executable and are also
the offsets used by rollback_snapshot.cpp. As a cChrInput-only copy,
CCHR_INPUT_SIZE = 0x5A0 is 0x30 bytes too large.

Other relevant fields:

    +0x2B70  cChrJointHold, size 0xE0
    +0x2C50  cChrMessage[6], six records of 0x30 bytes
    +0x2D70  cChrPause, size 0x10
    +0x2D80  mRandom, 0x10 bytes
    +0x2D90  mbRandomize and following identity/runtime state
    +0x3F38  mWeaponNum
    +0x3F48  animation request and transition state
    +0x4210  capsule primitives
    +0x4D10  capsule Vec3 cache
    +0x4E20  sphere bank 0
    +0x5530  sphere bank 1
    +0x5C40  sphere bank 2
    +0x6340  combat arrays and damage state
    +0x6490  cChrTargetInfo[5], five records of 0x80 bytes
    +0x6710  relationship/shot state
    +0x6718  linked-character pointer
    +0x6720  linked-character pointer
    +0x6728  linked-character pointer
    +0x6730  mpThrowPairChr
    +0x67F8  projectile hit repeat limit
    +0x67FC  projectile block repeat limit
    +0x6808  shot-group state
    +0x68C0  combat tail
    +0x68F0  concrete subclass tail begins

Range-by-range review
---------------------

1. +0x0028, +0x0048, +0x0080, +0x00A8, +0x012C

These are explicitly restored. They are small early cChr/input/action scalar
blocks. No confirmed omission was found in these ranges.

2. +0x01B0..+0x021F

Explicitly restored. This was an observed model/coordinate gameplay block.
The surrounding inherited model state remains intentionally ownership-aware;
it is not evidence that the whole model object should be flat-restored.

3. +0x029E..+0x02AF

Explicitly restored. This covers the known assist/action flag bytes.

4. +0x0550..+0x055F and motion slots +0x0560

The motion header is explicitly restored. Each of eight motion records then
restores scalar ranges at relative +0x08..+0x11F, +0x140..+0x15F, and
+0x168..+0x16F while retaining selected resource/allocation pointers.
This is intentional and currently supported by the separate motion, blend,
channel, joint-state, joint-index, and blended-joint regions.

5. +0x1300..+0x13E7

Explicitly restored through several ranges. This covers the animation timing,
request, transition, constraint, and state-check values identified in the
current investigation.

6. +0x14F0..+0x155F

Explicitly restored by:

    +0x14F0..+0x1517
    +0x1518..+0x152F
    +0x154C..+0x155F

The named flag words mChrF, mAnmF, mPrgF, mNotF, mNo2F, mDmgF, mEtcF,
mEt2F, mUsrF, and mDbgF are covered. The broad pointer pass can temporarily
damage packed values, but the final scalar ranges restore these bytes.

7. cChrAbility +0x1560..+0x1877

This is not wholly missing as resnap2 claimed. Native construction initializes
an MtArray at cChrAbility+0x10 with six 0x80-byte cChrAbility::Prim records. The
records therefore begin at character offsets:

    +0x1578, +0x15F8, +0x1678, +0x16F8, +0x1778, +0x17F8

The six explicit 0x70-byte ranges begin at those exact record starts. Contrary
to the earlier version of this document, they copy each Prim's saved vtable and
first 0x68 bytes of payload. They do not preserve the Prim headers live.

The remaining issue is policy precision:

    +0x1560..+0x1577  cChrAbility vtable/MtArray header
    +0x15E8..+0x15F7  first primitive tail
    +0x1668..+0x1677  second primitive tail
    +0x16E8..+0x16F7  third primitive tail
    +0x1768..+0x1777  fourth primitive tail
    +0x17E8..+0x17F7  fifth primitive tail
    +0x1868..+0x1877  sixth primitive tail

Ghidra confirms cChrAbility::Prim is an MtObject with mutable ability values,
not just presentation data. The current ranges mix object ownership state and
scalar payload, then leave each final 0x10 bytes to the generic pointer policy.
The separate +0x1870 size 8 range restores the upper half of the sixth tail, and
+0x1644 size 4 overlaps the second record payload. This is an inconsistent
classification, not proof that every omitted tail byte must be copied.

The required policy is to keep the cChrAbility and six Prim vtables plus the
MtArray ownership header live, while restoring reader-confirmed mutable fields,
including any gameplay tail fields, deterministically.

8. cAtkCtrl +0x1878..+0x21C7

This is also not wholly absent. The broad body copy restores all non-pointer
bytes, and the existing explicit ranges include +0x1898..+0x18C7. The three
32-entry target tables are separately repaired at character offsets:

    +0x18C8, +0x1BC8, +0x1EC8

Each TargetInfo entry is 0x18 bytes. The restore accepts the saved raw target
pointer at entry +0x08 when it is null, unchanged, or a roster character, and
restores the eight scalar bytes at entry +0x10. This matches Ghidra's cAtkCtrl
TargetInfo layout of mTotalHit and mHitTime, but is validation rather than true
saved-to-live remapping.

The header is not represented by a correct field policy. The explicit
+0x1898..+0x18C7 copy corresponds to cAtkCtrl-relative +0x20..+0x4F. It already
forces mpResource and all of these scalars from the snapshot:

    mpResource / resource relationship
    mAtkInfoId
    mFlag
    mTotalCombo
    mDelayTime
    mLifeTime
    mCountTime
    mEndTime
    mAnmNo

mpUnit at relative +0x10 remains subject to the broad pointer heuristic, while
mpResource at relative +0x20 is currently raw-restored by the explicit range.
Thus the issue is not missing scalar coverage in this header; it is an unsafe
owner/resource policy. This should be fixed as a manifest, not by blindly
copying cAtkCtrl's MtArray headers or resource pointers.

9. cChrInput +0x21C8..+0x2737

Ghidra gives cChrInput a size of 0x56C; its aligned extent before mCmdSpatk is
0x570. Restore copies 0x5A0 bytes, ending at +0x2768. The final 0x30 bytes copy
saved mCmdSpatk+0x00..+0x2F, including its vtable and the beginning of
cChrCmdLimit, after the pointer-preservation pass. This is a confirmed object-
boundary over-copy. The copied vtable is normally the same image address, so
corruption or a desync from this alone is not yet proven. CCHR_INPUT_SIZE should
be 0x570 and command state should be handled by its own explicit policy.

10. cChrCmdSpatk +0x2738..+0x294F and cChrCmdCombo +0x2950..+0x2B67

The embedded command objects are not wholly missing, but their scalar policy is
incomplete. Current explicit ranges only force the cChrCmdLimit animation-mask
triplets and a small adjacent state block.

Ghidra confirms cChrCmdLimit contains gameplay restrictions for:

    life, gauge, recoverable life, status, ability, animation, height,
    jump/air-special counts, HVR count, all character flag masks, combined
    program/ability masks, user masks, and the user-function enable flag.

Those fields are copied by the broad body restore unless the pointer heuristic
misclassifies their qwords. The correct statement is therefore:

    Both command matcher objects lack an explicit scalar/pointer manifest.

The external line allocations also need review. Snapshot capture currently adds
the line allocation with ownerSlot 0. That means the owner-slot validation used
for other external buffers is not available if the matcher reallocates its line
array. The line payload is captured, but its restore is address-dependent rather
than owner-dependent.

The command owner and static command resource should remain live/remapped;
mutable matcher progress, success fields, usage counters, cChrCmdLimit scalar
fields, and cChrCmdBtnChrg scalar fields should restore from the saved timeline.

11. cChrJointHold +0x2B70..+0x2C4F

No dedicated restore exists. This is a confirmed policy gap, not a confirmed
byte omission: ordinary scalar bytes still come from the broad body copy unless
the qword heuristic misclassifies them.

Ghidra confirms gameplay-relevant fields:

    +0x08  mpUnit
    +0x18  mpTarget
    +0x20  mTargetJointP
    +0x24  mTargetJointA
    +0x28  mTargetJointOP
    +0x2C  mTargetASymType
    +0x30  mTargetOPSymType
    +0x34  symmetry flags
    +0x40  mPosOfs
    +0x50  mAngleOfs
    +0x60  mTargetMtx
    +0xA0  mTargetMtxOP

cChrJointHold__update and __syncTargets use these values to move a target
character, update its orientation, copy matrices, and propagate updates to its
weapons. This is not a presentation-only object.

Required policy: preserve its vtable, restore scalar selectors, flags, offsets,
and matrices, and remap mpUnit/mpTarget to live objects. No separate allocator
header has been established in this 0xE0-byte object.

12. cChrMessage[6] +0x2C50..+0x2D6F

No dedicated restore exists. The constructor sets every record's mpChr at
record +0x08 to the
owning cChr and assigns fixed types 1 through 6. These are self-owner pointers,
not six dynamic target relationships. Preserve/rebuild each vtable, self pointer,
and fixed type; restore mMsgF, mChrId, and mAnmNo. The broad copy already does
this in the common case, so this is an explicit-policy recommendation rather
than evidence that message payloads are currently absent.

13. cChrPause +0x2D70..+0x2D7F

No dedicated restore exists. mMode at +0x2D78 and mbDisable at +0x2D7C are
small scalar fields. The broad body copy normally restores them. An explicit
range would prevent pointer-shape misclassification while retaining the embedded
vtable, but no current omission has been demonstrated.

14. cChr random/identity +0x2D80 onward

The previous report had incorrect labels around this area. Correct layout:

    +0x2D80..+0x2D8F  mRandom, restored by the character RNG path
    +0x2D90           mbRandomize and adjacent state
    +0x2D9C onward    identity fields as shown by the exported structure

The RNG itself is handled separately and is not a missing restore. The
mbRandomize/adjacent state and identity/runtime bytes lack a clean explicit
manifest, but they are not all automatically gameplay-critical. They should be
classified from their readers before adding a broad range.

15. +0x3F38..+0x40D3

The main restore covers mWeaponNum and begins its animation/state range at
+0x3F48. The previous report described +0x3F3C..+0x3F47 too confidently. That
12-byte interval is not in the explicit range; it receives only the broad body
copy unless the pointer guard keeps it live. It remains unclassified rather than
proven gameplay scalar state.

The ordering concern is not confirmed by the inspected restore path. The
post-restore tail reapplies EP counts and selected throw/attack blocks, but the
document has not identified a specific native restore-time call that rewrites
all of these animation selectors. The following fields remain candidates for
ordering verification:

    mThrowAnmNo
    mTdownAnmNo
    mThrowAnmNoEPLast
    mTdownAnmNoEPLast
    mEPCnt

Do not add ranges until a post-repair comparison proves one is rewritten.

16. Collision primitives +0x4210..+0x62FF

The restore explicitly repairs scalar geometry for capsules and three sphere
banks, and captures external animation blocks. Parent pointers are retained
live because their target ownership graph is not reconstructed by the body
restore. This is intentional, but it is a conditional correctness assumption:
the live parent topology must match the saved character topology.

The current evidence does not prove that every parent pointer is missing. It
proves that parent pointers are not remapped. This should be treated as a
separate collision-topology audit, not as a reason to flat-copy the primitives.

17. +0x6340..+0x6427

The explicit ranges +0x6340 size 0x10 and +0x6360 size 0xC8 leave a 16-byte
explicit-policy hole:

    +0x6350 mComboDmgRate
    +0x6354 mComboGaugeRate
    +0x6358 mHVRDmgRate
    +0x635C mDHCDmgRate

These registered gameplay properties are reset together by
cChr__resetHitstunAndAtkMultipliers and affect damage/gauge calculation. They
are normally restored by the broad body copy, but can be retained live whenever
their packed qwords look like aligned addresses. They need an exact +0x6350
size 0x10 scalar range. +0x6360..+0x6427 is explicitly covered.

18. +0x6428..+0x648F last-created shot and shot groups

`cChr__createProperty` establishes an 8-byte mpLastCreateShot at +0x6428,
mCurrentShotGroup at +0x6430, eight animation serials at +0x6434..+0x6453,
and eight hit latches at +0x6454..+0x645B. Current explicit coverage is only
+0x6428 size 4. Because the pointer overlay first restores the full live qword,
that four-byte copy produces saved-low/live-high halves. It equals the intended
saved pointer only when both addresses share the same upper 32 bits; otherwise
it is a hybrid qword. Shot reconstruction remaps cChr+0x90 only; the inspected
code contains no +0x6428 remap.

mpLastCreateShot must be remapped through shot identity or cleared. The missing
remap is a confirmed defect whenever shot reconstruction changes the allocation;
the partial-copy damage depends on the saved/live address upper halves.
+0x6430..+0x645B is registered mutable shot-group state. It is broad-restored in
the common case, but lacks explicit protection from qword misclassification.
+0x645C..+0x648F remains insufficiently mapped.

19. cChrTargetInfo +0x6490..+0x670F

Five 0x80-byte target-info records are explicitly handled. The character pointer
at record +0x08 and the 0x70-byte payload are restored together only if the saved
pointer is null, unchanged, or a current roster character. If the saved pointer
fails that test, both the live pointer and live payload remain.

The previous report called the payload categorically missing. That was
incorrect. The remaining issue is that the validity rule does not remap saved
character identity to a different live allocation, and it intentionally keeps
the complete live record when the saved pointer is not accepted. For the fixed
roster this is usually safe; for helper/temporary character objects it is not
proven.

20. +0x6710..+0x67FF relationship and shot state

This is the highest-confidence remaining relationship-policy gap.

Ghidra proves these relationship slots are used by native post-sync and throw,
assist, partner, and DHC logic:

    +0x6718  cChr__getPointer6718 and linked-character logic
    +0x6720  validated/cleared by cChr__validateLinkedCharacter6720
    +0x6728  validated/cleared by uCharacterPost__sync
    +0x6730  set by uCharacterPost__sync from linked/throw state

Only +0x6730 is currently reapplied after shot reconstruction. The other three
are still subject to the generic live-pointer preservation behavior. Ghidra
confirms that normal frame-time uCharacterPost__sync validates all three and can
derive +0x6730 from +0x6720/+0x6728. However, Rollback_RestoreFrame does not call
uCharacterPost__sync. Therefore the earlier claim that post-sync modifies these
pointers during restore was false; the actual risk is that stale live upstream
relationships survive restore and influence the next native post-sync.

The evidence-backed conclusion is:

    +0x6718, +0x6720, +0x6728, and +0x6730 need one coherent saved-to-live
    relationship remap before the next simulation tick.

The current implementation assumes roster cChr allocations are stable and even
copies raw roster pointers in target-info and mpThrowPairChr fixups. A stable
roster-identity remap is more robust, but raw address equality is not itself a
demonstrated defect for fixed roster allocations. Saved pointers to retired
helper objects must become null or a reconstructed equivalent.

The surrounding scalar shot/relation bytes are not all proven missing. The
following are proven readers and should be explicit manifest candidates:

    +0x67F8  cChr__getShotHitLimit
    +0x67FC  cChr__getShotBlockLimit
    +0x6800  mShotDefenseType
    +0x6804  mShotMutekiType
    +0x6828  existing throw/reaction state
    +0x6840..+0x68BF existing attack-info/throw state coverage
    +0x68C4  cChr linked-character finalization latch

The exact names for all bytes in +0x6710..+0x68CF are not established, so
unclassified bytes should be reported as such rather than all being declared
missing.

Confirmed cleanup overrun
-------------------------

`Rollback_ClearStalePointers` scans 64 qwords beginning at cChr+0x6748. Native
evidence proves this auxiliary-reference table has 21 entries: cChr__cChr clears
0xA8 bytes there, and uCharacter__clearDeadAuxiliaryRefs loops 0x15 times.

    native table: +0x6748..+0x67EF, 21 qwords
    mod scan:     +0x6748..+0x6947, 64 qwords

The extra +0x67F0..+0x6947 interval is gameplay and concrete subclass state.
Cleanup zeros a nonzero qword there when it does not point to an object with an
accessible vtable and executable vtable+0x20 target. This is not literally a
DTI validation. The extra scan can erase projectile limits, defense types,
throw selectors, attack-info state, combat/link latches, and concrete character
fields after the main scalar and concrete-tail restore. For example, ordinary
small packed scalars such as +0x67F8/+0x67FC fail the callable-object test and
are zeroed whenever their combined qword is nonzero. Most of this interval is
not reapplied afterward. This is the highest-confidence defect found in this
review. `SLOT_COUNT` must be 21 and cleanup must never access beyond +0x67EF.

21. Concrete subclass tails +0x68F0+

GeneratedCharacterTailFields covers known DTI properties for character
subclasses. Those fields are restored. Unknown subclass bytes are still handled
by RestoreDetectedCharacterTailScalars(), which uses the same pointer-looking
heuristic and preserves neighboring bytes around detected pointers.

This is a coverage limitation, not a list of proven missing fields. The robust
solution is to generate an explicit per-DTI tail manifest from every known
value/reference property and then classify unknown embedded objects separately.

Final findings
--------------

Confirmed implementation defects:

1. Stale-pointer cleanup scans 64 entries at +0x6748, but native code defines
   21. It can zero +0x67F0..+0x6947 after restore.
2. +0x6428 is an 8-byte shot reference treated with a four-byte copy. This can
   form a hybrid qword when address upper halves differ, and no saved-to-restored
   shot remap handles the field when reconstruction changes the allocation.
3. The cChr pointer guard uses address shape without accessibility or field
   identity, so any unmanifested scalar qword can incorrectly stay live.
4. The cChrInput-specific copy crosses its 0x570 aligned extent by 0x30 bytes,
   raw-restoring mCmdSpatk+0x00..+0x2F outside the command object's policy.

Confirmed explicit-policy gaps or unsafe ownership handling:

1. +0x6350..+0x635F damage/gauge multipliers lack forced scalar coverage.
2. +0x6430..+0x645B shot-group mutable state lacks forced scalar coverage.
3. cChrJointHold lacks field-specific scalar and relationship handling.
4. Both cChrCmd objects lack a complete scalar/pointer manifest.
5. The two external command line buffers are captured without owner slots.
6. cAtkCtrl raw-restores mpResource while retaining mpUnit through a heuristic.
7. +0x6718, +0x6720, +0x6728, and +0x6730 lack one coherent relationship
   restore/remap policy.
8. +0x67F8..+0x6807 and the +0x68C0 combat/link tail lack complete explicit
   scalar policy, especially the +0x68C4 link-finalization latch.
9. Unknown concrete subclass tail fields still depend on heuristic detection.

Recommendations not backed by a demonstrated current mismatch:

1. Add explicit payload policy for cChrMessage. The broad copy normally restores
   mMsgF, mChrId, and mAnmNo already.
2. Add explicit scalar policy for cChrPause. The broad copy normally restores
   mMode and mbDisable already.
3. Replace raw roster addresses with stable roster identity. Current evidence
   does not show roster cChr allocations changing during rollback.
4. Verify animation-selector ordering with a post-restore comparison before
   adding more ranges.

Not proven missing after this review:

1. The whole cChrAbility range. Its scalar payload is mostly restored; its
   embedded headers/tails are not explicitly classified.
2. The whole cAtkCtrl range. Its scalar body is broadly copied and target
   tables are separately repaired; the header/pointer policy is unsafe.
3. The cChrInput payload itself. It is captured, but the current restore size
   overruns the payload and must be corrected to 0x570.
4. cChrTargetInfo payloads for null, unchanged, or current-roster targets. The
   complete live record is retained for rejected non-roster/helper targets.
5. The entire +0x3F3C..+0x3F47 interval. The previous report overstated this
   as a proven missing weapon range.
6. Every byte in +0x6710..+0x68CF. The relationship pointers and specific
   reader-confirmed scalars are missing from policy, but all unnamed bytes have
   not been proven gameplay-authoritative.

Recommended implementation order
---------------------------------

1. Fix `Rollback_ClearStalePointers` to use 21 entries and assert an end no
   greater than cChr+0x67F0.
2. Remap or clear the full 8-byte mpLastCreateShot at +0x6428.
3. Correct `CCHR_INPUT_SIZE` from 0x5A0 to 0x570.
4. Add exact/remapped policies for +0x6350..+0x635F,
   +0x6430..+0x645B, +0x67F8..+0x6807, and +0x68C0..+0x68CF.
5. Replace the current cChr body pointer heuristic with an explicit overlay
   manifest. Default unknown inline bytes to saved scalar bytes; preserve only
   named vtables, allocator headers, resource pointers, and lifecycle links.
6. Implement a single relationship remap for +0x6718/+0x6720/+0x6728/+0x6730,
   and run it after shot/effect reconstruction, before the next simulation tick.
7. Add explicit cChrJointHold, message, and pause manifests.
8. Add explicit matcher manifests and give command line buffers owner slots.
9. Add explicit cAtkCtrl header and target-table manifests.
10. Generate and audit concrete subclass tail manifests, and apply them after
   every pass that can mutate the character tail.

For the current throw desync, fix the cleanup overrun before drawing conclusions
from relationship state: the overrun itself reaches and conditionally zeros the
relationship-adjacent state through the concrete tail. After that fix, compare
the four relationship fields before the next uCharacterPost__sync. Static
analysis proves that +0x6718/+0x6720/+0x6728 feed normal native post-sync and
that +0x6720/+0x6728 can set or clear +0x6730, but does not prove this group is
the observed frame-2152 root cause.
